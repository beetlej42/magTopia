# MAGTOPIA（麦托邦）核心玩法设计

## 文档状态

- 版本：v0.2
- 状态：核心玩法当前基线，供 Simulation、服务端、Agent 与前端开发共同参考
- 优先级：先跑通基础循环，再扩展卡牌、职业成长、复杂事件链与长期离线演化
- 实施拆解见：[CORE_GAMEPLAY_IMPLEMENTATION_PLAN.md](CORE_GAMEPLAY_IMPLEMENTATION_PLAN.md)

> 本版本替代 v0.1 中的三个旧假设：
>
> 1. 资源、人口和暴露不再按连续自然时间积分，而是在游戏回合结算时统一变化。
> 2. 暴露事件不再由系统按魔法师人口自动处理，而由 Agent 在策略阶段派遣专职处理人员。
> 3. 猫头鹰日报的事实由系统生成并锁定，叙事和汇报由 Agent 根据事实完成。

## 1. 核心体验

MAGTOPIA 是一款由 AI Agent 驱动的魔法城市建设游戏。

玩家负责方向，Agent 负责经营与解释：

- 玩家通过卡片和自然语言影响城市方向。
- Agent 负责规划 district / block、修路、建设、升级与风险调整。
- 城市中的高魔法建筑带来魔力、魔法师人口和更强的发展能力，同时产生更高暴露风险。
- 普通城市功能为魔法活动提供社会与空间掩护。
- 暴露事件出现后，Agent 进入策略阶段，派遣合适的专职人员处理。
- 系统负责规则、随机数与事实结算；Agent不能自行决定骰子结果。
- Agent 最后根据系统提供的事实写猫头鹰日报，向玩家解释当天发生了什么、自己做了什么、下一步准备做什么。

核心体验不是让玩家微操城市，而是：

> 玩家与一个真正负责经营城市、会判断、会成功也会失败、并会回来汇报的 Agent 共同生活在一座持续积累历史的城市中。

## 2. 基础循环

一个完整游戏回合对应一个“城市日”。

```text
新回合开放
  ↓
读取上回合日报与玩家选择
  ↓
Agent 建设阶段
- 读取城市状态
- 规划 district / block
- 建筑与道路建设
- 调整普通/魔法建筑布局
  ↓
系统生成本回合暴露事件
  ↓
Agent 策略阶段
- 查看事件类型与难度
- 选择处理人员
- 给出派遣理由
  ↓
系统结算
- 属性/专长修正
- 系统掷骰
- 大成功 / 成功 / 失败 / 大失败
- 应用资源、人口、暴露、事件与人员状态变化
  ↓
系统冻结本回合事实
  ↓
Agent 编写猫头鹰日报
  ↓
回合结束，等待下一回合开放
```

第一版的重点是让这一条链能够完整运行，而不是先做大量内容。

## 3. 双时钟模型：自然时间触发，回合时间结算

MAGTOPIA 同时存在两个时间概念，但只有一套 Simulation 规则。

### 3.1 自然时间 `wallClock`

自然时间只负责调度：

- 什么时候开放新回合；
- 当前回合什么时候到期；
- Agent 是否在回合截止前完成操作；
- 是否需要系统自动关闭无人管理的回合。

自然时间本身不直接产生金币、魔力、人口或暴露变化。

### 3.2 游戏回合 `turn`

资源、人口、建设进度、暴露、事件和人员状态全部以回合为基本单位结算。

```text
错误：coins += hourlyIncome × realHours
正确：resolveTurn() -> 本回合获得 coins +42
```

因此 Agent 不能通过反复调用“推进时间”刷资源，也不能通过永远不结束回合冻结风险。

### 3.3 回合截止

MVP 默认一个现实时间窗口对应一个游戏回合，例如每天开放一个回合。

- Agent 可在窗口内主动完成本回合。
- 到达截止时间仍未完成时，系统自动关闭本回合。
- 无人处理的暴露事件不会无限暂停，而进入保守的自动结算路径。
- 自动结算的惩罚应温和，避免一天未上线导致城市灾难性崩溃。

长期离线如何压缩多个无人管理回合属于后续细节。MVP 只需要保证“回合不会永远等待 Agent”。

## 4. 基础经济与人口

第一版只保留四个核心量：

| 变量 | 含义 |
|---|---|
| `coins` | 普通建设、维护、公共事务和人员支出的通用资源 |
| `magic` | 魔法建设和高魔法活动的统一魔法资源 |
| `mugglePopulation` | 普通人口当前值与容量 |
| `wizardPopulation` | 魔法师人口当前值与容量 |

不再把 `timber`、`stone` 等作为核心玩法资源。

基础收入和建筑收入均按回合计算。

```text
本回合金币收入 = 基础收入 + 有效建筑产出 + modifier
本回合魔力收入 = 基础收入 + 有效魔法建筑产出 + modifier
```

人口同样在回合结算时迁入、迁出或重新分配。

## 5. 建筑 Gameplay Metadata

视觉 BuildingSpec 与玩法数据必须解耦。

体素设计负责“建筑长什么样”；Gameplay Metadata 负责“建筑在城市里意味着什么”。

MVP 每栋建筑至少需要：

```text
category
magicLevel
muggleCapacity
wizardCapacity
coinOutput
magicOutput
concealment
activity
jobs
exposure
status
```

建议将这组字段放在稳定、可版本化的 gameplay schema 中，不要散落在体素 grammar 或渲染参数里。

### 5.1 `magicLevel`

范围 `0..1`，同时影响：

- 魔法视觉表现；
- 建造成本；
- 魔力产出；
- 魔法师容量/吸引力；
- 活动强度；
- 暴露压力。

### 5.2 普通建筑作为掩护

低魔法建筑自然提供掩护，不需要额外的“掩护建筑”资源。

例如：

- 市场、车站、剧院、学校：较强掩护；
- 普通住宅、商店、工坊：中等掩护；
- 公园、空地：较弱掩护；
- 高魔法建筑：通常不提供普通掩护。

掩护是邻域派生值，而不是库存资源。

## 6. 建筑级暴露

城市没有一个统一的全局暴露条。高魔法建筑各自维护 `exposure`。

```text
exposurePressure =
  magicLevel
  × activity
  × visibility
  - neighborhoodConcealment
  + modifiers
```

本回合暴露变化只在回合结算时应用。

暴露风险的意义应当直接可解释：

> 这栋建筑风险高，是因为它过于魔法、活动过强，而周围没有足够普通、合理的城市生活来解释异常。

### 6.1 封锁

当暴露达到最终阈值，建筑进入 `sealed`：

- 停止产出；
- 停止提供人口容量；
- 不再作为有效掩护；
- 不能普通维修恢复；
- 保留在地图上并获得永久视觉痕迹；
- 成为城市历史中的“都市传说地点”。

失败不应该简单删除内容，而应该给城市留下记忆。

## 7. 暴露事件

暴露事件由系统根据建筑状态和回合规则生成。

事件至少包含：

```text
id
buildingId
type
difficulty
severity
summary
status
```

MVP 事件类型不必很多，但必须能够映射到不同处理能力。例如：

- `investigation`：未知异常、来源调查、魔法犯罪线索；
- `containment`：失控魔法、危险生物、空间异常；
- `concealment`：普通市民目击、舆论、记忆与现场伪装。

## 8. 专职事件处理人员

暴露处理能力不再直接等于魔法师人口。

### 8.1 人口与编制解耦

MVP 基线：

```text
每 10 名魔法师人口 -> +1 专职人员编制上限
```

这是“可雇佣上限”，不是自动获得人员。

因此魔法师人口增长会扩大城市潜在处理能力，但玩家/Agent仍需要花费资源形成真正的事件处理队伍。

职业名称暂定为 `Veil Warden / 帷幕守卫`，最终命名可以后续调整。代码层不要使用受外部 IP 强绑定的职业名。

### 8.2 人员属性

MVP 保持简单。每名处理人员至少包含：

```text
investigation
containment
concealment
specialties[]
status
```

可以有名字和少量叙事性格，但性格第一版不进入核心数值公式。

## 9. Agent 策略阶段

Agent 是事件处理决策者，不是随机数源。

Agent收到：

- 当前所有待处理事件；
- 事件类型和难度；
- 可用人员与属性；
- 人员当前状态；
- 城市资源与重要风险。

Agent负责：

1. 选择谁处理哪个事件；
2. 可以选择暂不处理某些事件；
3. 给出派遣理由；
4. 提交结构化 assignment。

系统负责验证人员是否可用、一个人是否被重复派遣等硬约束。

## 10. 系统骰与结果

随机数只能由系统生成并记录。

一个事件结算可以抽象为：

```text
roll + relevantAttribute + specialtyBonus + modifiers
vs difficulty
```

具体骰型、阈值和平衡参数后续可调，但结果固定分为四档：

- `critical_success` 大成功
- `success` 成功
- `failure` 失败
- `critical_failure` 大失败

失败不应只有数值惩罚，还应成为新的城市内容来源。

例如：

- 大成功：显著降低暴露，可能获得额外线索或人员成长；
- 成功：解决事件并适度降低暴露；
- 失败：事件残留、暴露继续增加或下回合再次出现；
- 大失败：事件升级、产生连锁事件、人员暂时不可用或带来额外城市后果。

系统必须把原始骰值、修正项、最终结果写入事件事实，确保可审计和可复现。

## 11. 猫头鹰日报：系统事实，Agent叙事

日报不再由纯模板作为最终玩家文本。

系统先生成不可篡改的 `TurnFacts`，例如：

```text
turn
resourceDelta
populationDelta
buildingsStarted
buildingsCompleted
exposureChanges
incidents
assignments
rolls
outcomes
sealedBuildings
```

Agent只能基于这些事实写故事和汇报，不能修改事实。

Agent日报应完成三个任务：

1. 告诉玩家实际发生了什么；
2. 解释自己为什么这样建设或派遣；
3. 给出下一回合准备怎么做。

因此日报本身是人机交互核心，而不仅是 UI 展示。

如果 Agent 缺席，系统可以保留结构化 TurnFacts 和一个最低限度的机器摘要；叙事日报可在 Agent 下一次上线时补写。

## 12. 玩家职责

玩家不负责日常微操。

MVP 中玩家主要通过：

- 每回合若干卡片中的一次选择或跳过；
- 自然语言方向性要求；
- 对 Agent 日报的反馈；

影响下一回合策略。

卡牌系统不是第一阶段 blocker。应先完成不带卡牌也能运行的基础循环。

## 13. Agent职责

Agent同时承担建设者、策略管理者和叙事者三个角色。

Agent负责：

- 读取城市与上回合事实；
- 规划 district / block；
- 建筑与道路建设；
- 调整魔法建筑与普通掩护布局；
- 读取暴露事件；
- 派遣合适的帷幕守卫；
- 解释决策；
- 根据系统事实写猫头鹰日报；
- 向玩家提出下一回合计划。

Agent不负责：

- 自己修改游戏时间；
- 自己生成资源；
- 自己决定随机骰结果；
- 修改已经由系统冻结的 TurnFacts；
- 绕过建设、预算、暴露或人员规则。

## 14. MVP 开发边界

第一版明确不追求：

- 大量事件类型；
- 复杂职业树；
- 装备系统；
- 人员永久死亡；
- 完整卡牌池；
- 长期离线 30+ 回合精细模拟；
- 复杂城市级政治系统；
- 独立里层魔法城市；
- 多人协作城市。

先验证这一件事：

> Agent 建设城市后，能否基于自己造成的风险做第二阶段策略决策，并把真实但带有个性的结果讲给玩家听。

## 15. MVP 验收标准

基础循环至少满足：

- CityState 使用 `coins`、`magic`、普通人口和魔法师人口作为核心经济状态；
- 资源和人口只在回合结算中变化，不按自然小时连续积分；
- 自然时间只负责回合开放和截止；
- 每栋建筑拥有稳定的玩法 metadata；
- `magicLevel` 能影响产出、成本和暴露压力；
- 普通建筑能通过邻域掩护降低高魔法建筑风险；
- 系统能生成至少三类暴露事件；
- 魔法师人口与事件处理能力解耦；
- 城市能雇佣具有不同属性的专职人员；
- Agent 能读取事件与人员，并提交结构化派遣；
- 系统独立掷骰并得到四档结果；
- 事件结果能改变暴露和城市状态；
- `sealed` 建筑成为永久城市记忆而不是 Game Over；
- 系统能够冻结一份完整 TurnFacts；
- Agent 能基于 TurnFacts 生成日报并解释决策；
- Agent 不推进时间、不生成随机事实；
- 回合即使没有 Agent 操作也不会无限悬停。
