# MagicTown 项目总纲

## 1. 项目定义

**MagicTown 是一座从空白开发地逐步生长为魔法伦敦式城市的放置型城市模拟。**

玩家是低频决策的市长：决定城市想成为什么样子；每位玩家拥有的一名市政 Agent 是高频执行者：在时间中建设、维护、解释并赋予城市风格。玩家下一次回来时，应当看见结构性的变化，而不只是数值上涨。

> 玩家投下方向与种子；Agent 用自己的品味，把它们变成一座值得远看、也值得靠近阅读的城市。

这不是传统的“玩家逐格盖楼”模拟器，也不是让 LLM 自由生成城市。它是一个**人设定愿景、系统保证城市可运行、Agent 负责取舍与叙事的共同创作系统**。

## 2. 核心体验与验收标准

每一项产品、程序和美术工作都应服务于下面的体验。

1. 玩家低频介入：一次操作表达一个有意义的愿景、规则或城市变量。
2. Agent 高密度工作：在玩家离开后持续做小而合理的建设与调整。
3. 变化必须可读：回来时能看出新片区、道路关系、功能变化或城市气质，而不是只看到资源数增加。
4. Agent 的品味必须可见：不应只存在于弹窗文字；它要写进建筑选择、街区关系、装饰、灯光和命名。
5. 城市要像城市：从空地开始，经历道路、住宅、商业、交通、公共设施与密度提升，而不是在自然景观中摆放孤立建筑。

最终检验问题：

> 玩家离开一段时间后，是否会迫不及待地回来理解“我的 Agent 为什么把这座城市变成了这样？”

## 3. 非目标与边界

第一阶段明确不做：

- 全自由镜头、可穿行的真实 3D 建筑；
- 让 LLM 看像素、逐格规划或直接生成网格模型；
- 复杂的多人实时经济、实时战斗或大量自治 NPC；
- 一开始模拟完整伦敦、完整交通经济或完整市民生活；
- 每生成一栋建筑都实时调用图像模型。

多人共享世界是后续扩展：先验证单玩家 + 单 Agent 的城市成长是否令人期待。

## 4. 游戏循环

```text
空白城市开发地
  -> 玩家设定方向 / 投放种子 / 审批大项目
  -> 系统更新需求、预算、可达性与地块价值
  -> Agent 选择发展策略并提交受限建设意图
  -> 求解器负责落位、道路与成本
  -> 资产系统选择已有建筑或异步生产新资产
  -> 世界渲染并持续演化
  -> 玩家回来阅读结果、日志与新的选择
```

### 玩家动作

玩家应控制“为什么”和“往哪里发展”，而不是每一个几何细节：

- 指定片区愿景：学院区、安静河岸、繁华商业街、保护旧街区；
- 放置种子节点：魔法遗迹、打人柳、市场许可、学院基金、车站计划；
- 批准 / 否决 Agent 的重大提案；
- 改变政策：保护、密度、夜间商业、魔法研究、安全等；
- 训练 Agent 偏好：生态、学术、浪漫、商业、历史保护等。

### Agent 动作

Agent 只操作高层语义，不操作像素或逐格坐标：

- 发展某片区及其功能定位；
- 请求连接两个语义节点；
- 在候选地块建立某类功能建筑；
- 选择建筑语言、命名、装饰和优先级；
- 提出建设日志及后续建议。

## 5. 世界：城市基底，而非自然大地图

每张地图是待开发的**魔法伦敦城区**。它开始时有城市地理和历史约束，但不应有完整的自然村庄或预制城镇。

### 第一张地图：河岸开发区

建议固定为一个可反复验证的最小城市片区：

```text
北侧：铁路高架、未来车站入口
西侧：河流或运河与可改造河岸
中央：空置砖地 / 旧工业用地
东侧：通往旧城区的外部道路
南侧：低密度旧街区边缘与一处魔法遗迹
```

城市会自然经历：

```text
空地
-> 第一条道路与第一项服务
-> 住宅、访客与商业需求
-> 车站 / 桥 / 学院等锚点
-> 连续街区、夜间活力与公共服务
-> 交通、密度、保护与改造的张力
```

当前原型的实现底座是 **Isometric Asset Terrain**：50×50 个逻辑城市地块，每个地块在渲染层细分为 4×4 个地形小面。一张连续的低模曲面先承载陆地、下沉水系与水岸。其上已有第一批**基础设施覆盖地块**：道路、人行道、小广场与口袋公园；它们不替换地形，必须采样同一高度场。河岸仍只保留原始水体与沙岸，待公共空间与码头方案确定后再加入人工构筑物。铁路、建筑、车辆、人物与密集绿化仍未进入地图。

基础地块以四边连接口（`north/east/south/west`）描述道路和步行连通性；同一组合同还声明路灯与广场地灯。灯光只承担夜间寻路与公共节点：白天保留轻微灯芯暖色，黄昏或 `nightLighting` 增大时提高发光和有限范围的点光源，不以全局魔法霓虹照亮城市。

地形由 seed 驱动的配方生成：一条窄的主河道以一次大尺度河套和轻微扰动形成曲线；一座旋转的平滑椭圆湖独立生成，并与河道保持间距。同一 seed 必须稳定复现同一地形，随机按钮只改变 seed。

### 世界状态

世界真实状态以 **Field-backed Graph** 表达：

```text
Terrain / urban fields
  水岸、微坡、建设成本、景观、可达性、魔法风险、地价

Semantic graph
  地块、建筑、片区、道路入口、河岸、车站、遗迹及它们的关系

Infrastructure graph
  道路、桥、步道、铁路、公共服务及容量
```

地形场为系统求解服务；Agent 看到的是压缩后的机会、约束和候选动作，例如“河岸景观值高、接近主路但有洪水风险”。

## 6. 模拟、Agent 与求解器的职责

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 模拟系统 | 预算、需求、容量、可达性、地价、风险与时间推进 | 文学创意与审美选择 |
| 求解器 | 选址、路径、桥位、连接成本、道路网络 | 决定城市想成为什么样子 |
| Agent | 愿景取舍、建设优先级、功能组合、风格、命名、日志 | 逐格寻路、像素理解、直接造 mesh |
| 玩家 | 长期方向、政策、种子、重大审批 | 高频维护与细节摆放 |
| 渲染器 | 将确定状态投影为可感知的城市 | 定义游戏规则 |

一个连接请求的正确形式是：

```json
{
  "action": "connect",
  "from": "willow_district",
  "to": "old_town_road_entry",
  "mode": "pedestrian_route",
  "priority": "visitor_access"
}
```

系统随后根据距离、坡度、水体、拆迁、现有道路和容量求得合理路线。Agent 提出“需要什么连接”，而非画出路径。

## 7. Agent 品味：A Pattern Language 的游戏化使用

Agent 的创造力应受约束但清晰可见。每个 Agent 有一组稳定、可逐步学习的偏好：

```text
价值观：生态 / 学术 / 商业 / 历史保护 / 浪漫
空间偏好：临水、低密度、连续街墙、花园、广场
建筑偏好：窄高立面、弯屋顶、暖窗光、温室、藤蔓
建设取舍：先交通、先公共服务、先景观、先收益
```

Agent 从受控 Pattern 库中选取并组合，而不是凭空发明不可执行规则：

```yaml
district_style: willow_magic
patterns:
  - waterside_walkway
  - quiet_front_garden
  - warm_lantern_rhythm
  - crooked_shop_roof
  - preserve_existing_trees
```

LLM 可以为此给出理由、名称、店铺故事和新组合建议；系统必须将这些选择落实为可见的空间关系与视觉参数。

## 8. 美术与渲染总路线

### 决策

**柔和等距低模建筑资产是建筑主表现；参数化低模是城市的连续空间和动态补充。Depth Anything / 2.5D 是让这些资产获得有限立体感的实现技术，而不是像素美术风格。**

```text
Soft isometric low-poly building assets
  可见屋顶、主立面与侧立面；独特轮廓、店招、学院、商店、重点建筑

Low-poly support layer
  地面、道路、河流、桥梁、铁路、树、路灯、人物、车辆、粒子

Runtime effects
  Depth Anything 视差、法线受光、阴影、雾、昼夜窗光、水面与魔法特效
```

建筑不追求真实可绕行的全角度模型。镜头保持高斜视正交或弱透视，允许有限视差和小角度观察；Depth Anything 深度图用于增加层次，而不是伪造自由 3D。

### 美术方向

目标是**清新、温暖、可亲近的魔法伦敦**：砖石、板岩、河岸、铁路与连续街区提供城市骨架；暖窗光、紫色/青绿魔法、温室与植物为少量明确的奇异点缀。

视觉北极星见 [VISUAL_TARGET.md](VISUAL_TARGET.md)，详细执行约束见 [ART_DIRECTION.md](ART_DIRECTION.md)。后续修改必须保留其核心的：

- 固定地块与相机合同；
- 可读的建筑轮廓与城市密度；
- 统一光照与有限魔法强调色；
- 建筑资产必须可独立摆放、可扩张。

低模环境与生成建筑资产必须共享同一套等距低模城市模型语言；不能把一方做成写实插画、另一方做成像素或糖果色积木。

## 9. 建筑资产合同

每个可摆放建筑都是一个可验证的等距低模城市资产，而不是一张无边界插画或正面平铺 sprite。

```json
{
  "assetId": "shop_willow_wand_001",
  "archetype": "tourist_shop",
  "footprint": "1x2",
  "floors": 3,
  "districtStyle": "willow_magic",
  "camera": { "yaw": 45, "elevation": 55, "projection": "orthographic" },
  "style": "soft_isometric_lowpoly_urban_diorama",
  "visualPatterns": ["crooked_roof", "willow_branches", "warm_windows"],
  "purpose": "visitor_service",
  "sourceNode": "whomping_willow_01",
  "slots": ["front_sign", "roof_decoration", "front_garden"],
  "maps": {
    "rgb": "rgb.png",
    "mask": "mask.png",
    "depth": "depth-anything.png",
    "normal": "normal-depth-anything.png"
  }
}
```

资产生产流程：

```text
Agent 提交结构化 Asset Spec
-> 系统套用固定 Prompt、地块和相机基准板
-> 图像生成候选
-> 去背景、裁切、mask
-> Depth Anything 深度图和法线图
-> 自动验收：比例、留白、可读性、地块占用、禁用元素
-> 写入 Asset Registry
-> Three.js Depth Relief 渲染与低模环境叠加
```

Agent 不直接写最终 Prompt。新资产应异步生产：建设期间可以显示施工围挡、低模施工体块或既有可复用资产，避免实时生图阻塞城市时间。

## 10. 第一版 MVP

目标不是完成城市，而是证明“离开后回来值得看”。

### 范围

- 一张固定河岸开发区地图；
- 一个玩家和一个市政 Agent；
- 3 类需求：居住、访客、工作 / 服务；
- 4 类可建设功能：道路连接、住宅、商店、公共 / 学院设施；
- 3 种 Agent 品味：生态浪漫、学院研究、商业活力；
- 一个特殊种子节点：打人柳或河岸魔法遗迹；
- 6--10 个符合资产合同的柔和等距低模建筑资产；
- 少量低模道路、河流、树、路灯与移动人物；
- 一段可读的建设日志。

### 成功条件

玩家放下同一个种子，在不同 Agent 偏好下，应看见可辨别的不同结果：

```text
生态浪漫：步道、植物园、茶馆、低密度灯光
学院研究：温室、研究小屋、图书馆附楼、规整路径
商业活力：魔杖店、展台、接驳站、更高夜间人流
```

如果视觉上只能看见同一种房子，或差异只能在弹窗文字中阅读，MVP 不算成功。

## 11. 实施顺序

1. **城市基底**：实现 `magic-london-terrain-001`——50×50 逻辑地块、4×4 地形细分、连续低模曲面、边缘无效格、河流与下沉水岸；地形已确认，并叠加第一批可拼接的道路、河岸与绿地基础地块。
2. **世界状态**：建立地块 / 节点 / 边 / 需求 / 预算的数据合同。
3. **最小求解器**：根据连接请求完成候选选址和低成本道路铺设。
4. **资产合同**：把现有 Depth Relief 资产管线提升为 `Asset Spec -> Registry -> Renderer`。
5. **等距低模城市展示**：做 6--10 个可复用建筑资产、地面道路、河流、人物与昼夜。
6. **单 Agent 回合**：输入世界摘要，输出受限意图、风格选择和日志。
7. **离线演化**：将一次玩家决策发酵为一段可读城市变化。
8. **多人扩展**：仅在单人闭环成立后，引入可见的邻近城市、跨城地标和低频合作。

## 12. 文档优先级

发生冲突时按以下顺序决策：

1. 本文档：产品定义、系统边界、架构与阶段目标；
2. `docs/VISUAL_TARGET.md`：整体风格与可玩城市模型的验收标准；
3. `docs/ART_DIRECTION.md`：美术、镜头、资产与色彩的执行标准；
4. 代码中的 TypeScript / JavaScript 合同：当前可运行的真实接口；
5. 单个资产的 `asset.json`：该资产的具体事实。

任何新增功能应先回答四个问题：

1. 它是否让玩家做了更有表达力的低频决定？
2. 它是否让 Agent 的品味以可见形式进入城市？
3. 它是否让城市产生可读的结构变化？
4. 它是否遵守等距低模建筑资产 + 低模连续环境的统一语言？

如果四个问题都是否定，暂不应进入项目。

面向多玩家存档、专属 Agent 链接、HTTP API、异步资产生产与服务端扩展的整体方案，见 [AGENT_CITY_SERVICE.md](AGENT_CITY_SERVICE.md)。
