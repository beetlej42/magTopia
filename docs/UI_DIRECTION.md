# MagicTown UI Framework v1

## Purpose

MagicTown 的 UI 是一套 **维多利亚魔法城市的市政叙事界面**。它不模拟现代仪表盘，也不做深色奇幻 RPG HUD；它的职责是让玩家在移动端清楚读到：城市发生了什么、Agent 为什么这样做、以及自己这一次的低频选择会把城市带向哪里。

具体页面、卡牌内容、新闻标题和按钮数量可以变化；本规范只固定视觉语言、信息层级和交互边界。

## Product role

玩家是市长，不是逐格建造者。UI 应优先承载：

1. **回访阅读**：Agent 在玩家离开期间带来的可验证城市变化；
2. **方向选择**：片区愿景、政策、种子和每日随机抉择；
3. **提案审批**：对有意义的建设计划表示支持、反对或要求调整；
4. **城市观察**：在世界画面中理解道路、河岸、街区和魔法锚点的变化。

因此，默认界面中不出现建筑商城、逐格放置器、裸露的 seed/API 参数或工程调试表单。它们属于 Studio/开发工具，不属于玩家 UI。

## One-sentence visual direction

**一份在晴朗魔法伦敦中送达市长桌前的维多利亚市政公报。**

城市保持 [柔和等距低多边形城市模型](VISUAL_TARGET.md) 的明亮、可读与温暖；UI 像可翻阅的新闻纸、档案夹、信件和蜡封，而不是把整屏盖成古董道具。

## Visual pillars

### 1. Bright civic magic

- 默认是晴天/午后、高明度城市；深色只用于文字和细窄的结构线。
- 魔法是城市中少量可追踪的异常：遗迹、符文温室、奇异植物、学院仪器、魔法路灯或橱窗，不是全屏紫光。
- 每个关键魔法色都应指向一个对象、事件或选择；不能只是装饰性泛光。

### 2. Victorian print, not Victorian clutter

- 使用新闻纸、铜版画、档案标签、蜡封、细线边框和有限的新艺术曲线来建立年代感。
- 版面优先于装饰：一张卡只保留一个主标题、一个图像焦点和一个明确操作。
- 不使用厚重黑木框、满屏黄铜雕花、褶皱羊皮纸背景或模拟旧纸噪点来替代信息层级。

### 3. The city remains the hero

- 世界画面通常占可视高度的 55% 以上；UI 像临时叠放在城市上的公报，而不是永久控制台。
- 面板打开时仍应保留城市的关键地标、片区高亮或事件现场，形成“文字—地点”的对应。
- 叙事插图可以是铜版画风，但城市主画面不能退化为写实插画或像素画。

### 4. One decision, visible consequence

- 每次主要操作只要求玩家回答一个城市层面的选择。
- 选择应明确关联到片区、Agent 意图、成本/取舍或预期结果，而非只给抽象数值。
- 选择结果必须能回到后续日报、城市高亮和 Agent 日志中被看见。

## Surface and hierarchy

UI 由四层组成；任一时刻最多突出一层主任务。

| 层级 | 用途 | 典型载体 | 视觉权重 |
| --- | --- | --- | --- |
| 城市画面 | 观察、定位、事件现场 | 等距城市与轻量热点 | 最高 |
| 市政状态 | 城市名、日期、少量关键状态 | 顶部细条/徽章 | 低 |
| 叙事内容 | 日报、Agent 汇报、提案 | 公报页、信件、档案卡 | 中高 |
| 决策动作 | 批准、讨论、选择愿景/政策 | 底部卡或操作列 | 最高（仅在需要决定时） |

### Default mobile composition

```text
┌────────────────────────────┐
│ 城市名 · 日期 · 少量状态    │  市政状态
│                            │
│        可操作城市画面        │  城市画面
│    事件现场 / 片区轻高亮     │
│                            │
├────────────────────────────┤
│ 公报 / Agent 提案 / 每日卡   │  叙事与决策
│        一个主要选择          │
└────────────────────────────┘
```

日报、提案和每日卡是可替换的内容容器，不是固定页面顺序。它们可合并为一次回访流程，也可在城市中由热点重新打开。

## Style tokens

### Palette

UI 从城市调色板取色，但降低饱和度、提高纸面可读性。

| Token | Suggested value | Use |
| --- | --- | --- |
| `paper-base` | `#F3E5C9` | 主纸张与轻面板 |
| `paper-shadow` | `#D9C8A7` | 层叠纸边、分区 |
| `ink` | `#28394D` | 标题、正文、图标 |
| `slate-trim` | `#596477` | 结构边线、次级容器 |
| `oxblood` | `#81454A` | 警示、否决、重要印章 |
| `bottle-green` | `#3D6B5D` | 批准、生态、正向选择 |
| `brass` | `#BE9A57` | 极少量重点、徽章、选中态 |
| `magic-violet` | `#8068B7` | 魔法相关热点与稀有选择 |
| `magic-teal` | `#6DBCB2` | 与紫色互斥的第二魔法强调 |

- 页面底色以纸色、城市蓝绿和浅灰为主；不要以纯黑、深紫或厚重大面积棕色做底。
- 单个组件最多使用一种语义强调色；紫色和青绿不可同时抢占同一层级。
- 颜色语义稳定：绿 = 支持/生态，赭红 = 风险/反对，紫/青绿 = 魔法主题，金 = 重点但不等于默认按钮。

### Typography

- **Display serif**：城市名、日报名、主要标题。选择具备维多利亚书报气质但屏幕小字号仍清楚的衬线字体。
- **Readable sans**：正文、按钮、数值、筛选和表单。优先人文无衬线，避免仿古字体承担长段阅读。
- **Mono / small caps（可选）**：日期、编号、来源和事实标签；只做辅助信息。
- 标题最多两级；正文优先 15–17px 等效字号；按钮文字避免全大写。
- 字体负责年代感的 70%，装饰只负责剩余 30%。

### Materials and edges

- 主容器：平整哑光纸张，极细暖灰边线，轻微投影即可区分层级。
- 次级容器：浅色卡纸或半透明浅灰蓝玻璃；必须比城市背景更易读。
- 印章、夹子、徽章可作为“稀有节点”的强调，不应成为每张卡的默认装饰。
- 圆角建议 12–18px；纸页可使用不规则边角但不能影响按钮点击范围。
- 纹理只在大面积纸面以低对比度出现，禁止影响文字对比度。

### Iconography and illustration

- 图标使用单色或双色的线描/剪影，线宽一致，带少量几何感。
- Agent 肖像使用档案照、硬币浮雕或铜版画小像的构图，不做现代社交头像卡。
- 事件图可采用铜版画、地图标记或城市局部快照；优先让它与真实城市位置对应。
- 不使用卡通 emoji、科幻霓虹符号、厚黑描边或写实照片拼贴。

## Component contracts

以下是外观与信息职责的合同，不是限制功能的组件清单。

### Gazette / city chronicle

- 用于回访总结与可追溯事件叙事。
- 结构：报头 → 一条事实主标题 → 城市地点/插图 → Agent 来源或简短解释 → 进入详情。
- 事实、Agent 解读、玩家选择结果应视觉区分；日报不能成为唯一事实来源。
- 允许多篇，但首屏只突出一篇“本次变化最大”的头条。

### Proposal / approval sheet

- 用于 Agent 希望玩家介入的重大事项。
- 必须回答：发生在哪里、为什么现在要做、会如何改变城市、玩家能做什么。
- 操作应为语义选择，如“批准”“讨论”“暂缓”；不能把内部工程命令直接暴露给玩家。
- 可用片区小地图或城市高亮建立地点感，不要求玩家指定每一格。

### Daily choice card

- 用于每天一次或有限次数的随机抉择。
- 一张卡一个现象、两个到三个互斥方向；每个方向有简短的城市后果提示。
- 卡面可以是蜡封信、通告、占卜条或剪报，但交互机制必须一致：看见 → 选择 → 生效 → 后续可追溯。
- 随机不等于惩罚；避免让玩家因不了解隐藏规则而作出不可逆损失。

### City map and hotspots

- 地图/城市画面用于观察和阅读，不是精细放置器。
- 高亮使用低饱和轮廓、柔和描边、局部粒子或微弱色洗；不要遮住道路和建筑轮廓。
- 点击热点可打开对应日报、提案、片区或事件；无热点时城市画面保持干净。

## Interaction and motion

- 主要操作区固定在拇指易达的底部；最小点击热区 44×44 CSS px。
- 底部叙事面板支持上拉展开、下滑收起；展开后不应超过可视高度约 65%，必须保留城市上下文。
- 报纸打开：从事件地点或顶部通知“轻滑入”，时长约 220–320ms；不要模拟缓慢翻书阻断操作。
- 选择确认：蜡封/印章短暂落下、城市对应地点出现同色轻量反馈；避免长时间粒子或全屏闪光。
- 动效服务于“来源—选择—结果”的因果关系；尊重系统的减少动态效果偏好。

## Responsive rules

### Portrait first

- 以 360–430 CSS px 宽度作为主要设计范围；城市优先，内容通过底部抽屉分层出现。
- 顶部状态条不超过约 64px；任何状态都可收起为一个徽章。
- 长文本进入独立阅读页或展开态，不能无限拉长首页卡片。
- 使用 `dvh` / safe-area inset 处理移动浏览器地址栏与底部手势区。

### Landscape support

- 城市画面继续占主区域；叙事容器改为右侧/左侧 320–400px 宽的阅读栏，或底部横向抽屉。
- 不将竖屏底部抽屉简单旋转；横屏仍要保留可见城市和单手不重要、双手可操作的节奏。
- 同一时刻只显示一个主侧栏，避免左右两块控制台夹住城市。

## Accessibility and readability

- 正文与纸面保持至少 WCAG AA 级对比；颜色绝不作为唯一状态提示。
- 按钮文案用动作 + 对象表达含义；避免仅用图标或“确认/取消”。
- 纸张纹理、铜版画和装饰线必须能在开启高对比度或减少动态时降级。
- 支持屏幕阅读顺序：城市状态 → 叙事事实 → 选择影响 → 可行动作。

## Explicit non-goals

- 黑暗哥特、阴雨夜景、黑木黄铜满屏装饰；
- 现代 SaaS 仪表盘、玻璃拟态、赛博霓虹；
- 像素滤镜、粗黑描边、糖果色独栋童话村；
- 用“建筑商城 / 地块尺寸卡 / 拖拽摆放”表达玩家玩法；
- 把 Agent 的原始日志、API 数据或调试参数直接展示给玩家。

## Review checklist

每个新增页面或组件进入实现前，检查：

1. 玩家是否一眼知道自己正在阅读城市事实、Agent 意图还是做一个选择？
2. 是否仍能看见与文字有关的城市地点或片区？
3. 维多利亚感是否来自排版、纸张、印刷与市政叙事，而不是把界面做暗、做旧、做满？
4. 魔法是否以少量、可解释、可追踪的对象出现？
5. 竖屏拇指区、文本对比度与安全区是否成立？
6. 这个交互是否符合“玩家定方向，Agent 负责高频建设”的产品边界？
