# Hotfix — Mobile Card Interaction

## Goal

Fix the player-facing card selection flow on mobile Safari where the card UI is visible but taps do not produce any interaction.

This is a narrow hotfix. Do not change gameplay rules, card catalog contents, turn semantics, city-day phase semantics, or placement authority.

## Observed symptom

On iPhone Safari, the three-card choice overlay renders correctly, but tapping anywhere on the cards produces no visible response. Tapping a special-structure card does not even open the local `自己放置 / 交给 Agent` choice, which means the failure occurs before the authoritative `/cards/select` POST.

## Root-cause hypothesis to address

The city-day overlay currently relies on a parent `pointer-events: none` with child layers restoring `pointer-events: auto`:

```css
.city-day-experience {
  pointer-events: none;
}
.city-day-experience > * {
  pointer-events: auto;
}
```

This is fragile for a full-screen fixed overlay on mobile Safari and can leave the visible card UI outside the browser's effective hit-testing path.

Separately, controller JSON POSTs currently serialize request bodies without guaranteeing `Content-Type: application/json`. Once pointer interaction is fixed, this can still break `/cards/select`, `/cards/place`, `/site-searches`, and report dismissal on a real Fastify request path.

## Required implementation

### 1. Make overlay interactivity explicit

Do not depend on parent `pointer-events: none` + child `auto` inheritance tricks for modal interaction.

The city-day experience must explicitly switch between two modes:

- **interactive overlay mode**: when Owl Daily, three-card choice, special-structure mode choice, or manual placement controls are open, the full-screen city-day experience layer must receive pointer/touch events reliably.
- **pass-through mode**: when no modal player interaction is open (morning waiting, day, night, passive viewing), the overlay must not block the underlying Three.js viewer.

Use explicit state/class/attribute such as `is-interactive` or `data-interactive="true"`; exact naming is implementation choice.

Required behavior:

```text
report open          -> overlay interactive
card choice open     -> overlay interactive
mode choice open     -> overlay interactive
placement UI open    -> overlay interactive
all above closed     -> overlay pass-through
```

Do not disable the existing near/far camera behavior outside modal interaction.

### 2. Preserve direct local special-card response

Tapping a `special_structure` card must synchronously produce the local `自己放置 / 交给 Agent` choice before any network mutation is needed.

This is the simplest acceptance check that DOM hit testing and click delivery work.

### 3. Guarantee JSON request content type

In `cityDayController` request plumbing, any request with a JSON body must send:

```http
Content-Type: application/json
```

Do not overwrite an explicitly supplied caller content type.

Authorization behavior remains unchanged.

This must cover at least:

- `/cards/select`
- `/cards/place`
- `/site-searches`
- `/city-day/report-dismissed`

### 4. Keep city viewer pointer behavior isolated

When the card/report modal overlay is interactive, pointer gestures must not leak through to the city canvas.

When the overlay returns to pass-through mode, city orbit/pan/near-far gestures must work as before.

Do not add global `preventDefault()` handlers that permanently suppress the viewer.

## Tests

Add regression coverage at the DOM/event boundary, not only callback-level controller tests.

At minimum prove:

1. opening three-card choice marks the experience as interactive;
2. dispatching a real click/pointer-compatible DOM event to a card button invokes selection;
3. tapping a special-structure card opens `自己放置 / 交给 Agent` without requiring a POST first;
4. closing card/report/placement layers returns the experience to pass-through mode;
5. JSON POST requests generated by the controller include `Content-Type: application/json`;
6. existing URL-prefix and `expected_city_version` regressions remain green.

If the current test environment cannot emulate iOS Safari exactly, test the explicit interaction-state contract rather than relying on browser-specific parent/child pointer behavior.

## Acceptance

On iPhone Safari:

- the card overlay is visible and immediately tappable;
- special-structure card tap immediately opens `自己放置 / 交给 Agent`;
- resource/policy card tap reaches the server successfully;
- no click-through rotates/pans the city while the modal card layer is open;
- after the modal layer closes, city touch gestures work normally;
- no gameplay or turn semantics change.

## Out of scope

- card visual redesign;
- new animations;
- gameplay balance;
- new card types;
- city-day state-machine changes;
- new Agent behavior;
- changes to authoritative placement validation.
